## 1. 当前实现

- 路由：共享历史前缀目录下的请求数、阈值、工作量及淘汰损失代理；在途请求原子登记、失败释放、流式转发。
- CPU 保存：借鉴 EfficientAgent 的工作集条件化准入，使用真实 CPU 驻留/容量淘汰遥测，冻结首次决定，过期遥测恢复正常保存。
- 数据：公开 Coding Agent 文本轨迹转换、代码前缀机制负载、会话顺序和工具间隔保持的回放。
- PD：独立 P/D 策略入口，严格 KV 元数据交接、失败可观测，禁用 localhost HTTP 代理继承。
- 工具：进程组清理、唯一运行目录、配置/版本/源码哈希留存、逐请求流式指标与服务 counter 快照。

这些是实验原型，不是 Preble/EfficientAgent 的完整复现；路由目录当前明确标注为历史推测，尚未连接真实 GPU KV events。淘汰项是代价代理，不是精确物理 victim 预测。

### 2.1 默认算子路径不通过本机正确性验收

默认路径下 0.6B 和 3B 输出异常重复字符；切换 V1/V2 runner 不能独立解决。相同 3B 权重的 Transformers eager reference 返回正常结果。

直接 RMSNorm 探测中，预填 123 的输出 tensor 在调用已注册 CUDA 自定义算子并同步后仍保持 123，明显不符合 RMSNorm 行为。具体二进制/硬件问题尚未完成归因；不能把异常默认路径作为性能基线。

当前工作配置为 native RMSNorm、禁用自定义算子、Triton attention、eager。3B 基本问答通过。正式对照统一使用该配置与 V1 runner，性能不能直接代表健康的默认 CUDA 算子路径。

原始排查日志位于 `/root/autodl-tmp/outputs/kv_aware_20261019/`，包括 `smoke_06b*`、`smoke_3b*` 与参考检查记录。

### 2.2 数值一致性边界

一般代码提示在不同 runner/容量配置间存在 greedy 输出分歧，原始 `cpu_restore_correctness.json` 的 exact-match 为 false。后续观测到首 token 的 BF16 候选平分，但这尚不足以完全解释所有分歧，不将失败记录删除或直接称为全部无损。

追加的稳定答案探测使用足够多的独立前缀挤出 GPU 缓存，三组问题均有明确 LMCache `Retrieved 768` 记录；首次、CPU 恢复后及参考输出分别一致为 4、8、20。证据见 `cpu_restore_confirmed_probes.json`。它构成基本机制验收，不代表完成全面模型质量评估。

### 5.3 追加目录改造的语义

代码阅读发现本分支 KV manager 可在 allocation 时发出 BlockStored，故它只证明引擎缓存索引公告，不单独证明 GPU 写入完成。新增事件目录将其与路由观察到的成功完成前缀相交；BlockRemoved/缺口/清空撤销确认，重放在完整结束后原子发布，禁止短暂暴露历史存储。真实 ZMQ 发布器、连续前缀、epoch/缺口、取消/读取失败等 19 项测试及原有调度相关 31 项回归已通过。GPU 在线目录消融仍待运行，不从单测推断性能收益。
