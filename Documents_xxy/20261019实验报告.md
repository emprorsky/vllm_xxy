## 1. 当前实现

- 路由：共享历史前缀目录下的请求数、阈值、工作量及淘汰损失代理；在途请求原子登记、失败释放、流式转发。
- CPU 保存：借鉴 EfficientAgent 的工作集条件化准入，使用真实 CPU 驻留/容量淘汰遥测，冻结首次决定，过期遥测恢复正常保存。
- 数据：公开 Coding Agent 文本轨迹转换、代码前缀机制负载、会话顺序和工具间隔保持的回放。
- PD：独立 P/D 策略入口，严格 KV 元数据交接、失败可观测，禁用 localhost HTTP 代理继承。
- 工具：进程组清理、唯一运行目录、配置/版本/源码哈希留存、逐请求流式指标与服务 counter 快照。

这些是实验原型，不是 Preble/EfficientAgent 的完整复现；已提供历史目录和真实 KV events + 请求完成确认目录两条路径，并完成在线消融。淘汰项是代价代理，不是精确物理 victim 预测。

### 2.1 默认算子路径不通过本机正确性验收

默认路径下 0.6B 和 3B 输出异常重复字符；切换 V1/V2 runner 不能独立解决。相同 3B 权重的 Transformers eager reference 返回正常结果。

直接 RMSNorm 探测中，预填 123 的输出 tensor 在调用已注册 CUDA 自定义算子并同步后仍保持 123，明显不符合 RMSNorm 行为。具体二进制/硬件问题尚未完成归因；不能把异常默认路径作为性能基线。

工作配置使用 native RMSNorm、禁用自定义算子、Triton attention 与 V1 runner；eager主线和FULL_DECODE_ONLY Graph扩展分别统计，每组A/B执行模式相同。基本输出与小规模代码生成探测通过。性能不能直接代表健康的默认CUDA算子路径。

原始排查日志位于 `/root/autodl-tmp/outputs/kv_aware_20261019/`，包括 `smoke_06b*`、`smoke_3b*` 与参考检查记录。

### 2.2 数值一致性边界

一般代码提示在不同 runner/容量配置间存在 greedy 输出分歧，原始 `cpu_restore_correctness.json` 的 exact-match 为 false。后续观测到首 token 的 BF16 候选平分，但这尚不足以完全解释所有分歧，不将失败记录删除或直接称为全部无损。

追加的稳定答案探测使用足够多的独立前缀挤出 GPU 缓存，三组问题均有明确 LMCache `Retrieved 768` 记录；首次、CPU 恢复后及参考输出分别一致为 4、8、20。证据见 `cpu_restore_confirmed_probes.json`。它构成基本机制验收，不代表完成全面模型质量评估。

**加强验收推翻了此前仅凭简单算术探测的乐观判断。** `checks/cpu_prefix_fidelity/manifest.json` 状态为 failed：8 个 Coding 提示与 3 个前缀事实提示均有真实 CPU 读取，但全部触发 next-token 概率偏差告警。Coding 提示冷计算与 GPU APC 的 top-20 重合率为 0.95～1.0，CPU 恢复后为 0.45～0.75，共同 token 的最大 logprob 差约 1.86～5.73，不能归为普通 BF16 噪声。

事实探测中第一例冷计算/GPU 返回 marigold，CPU 恢复丢失该事实；另两例冷计算本身也未正确取回事实，且原内容判定过于严格，因此不能把三例内容失败全部归因于 CPU 恢复。原始输出、冻结的概率阈值和日志均保留。后续已通过逐元素检查定位复制布局错误，见第 7 节；小规模修复验收仍不等于全面质量无损。

### 5.3 追加目录改造的语义

代码阅读发现本分支 KV manager 可在 allocation 时发出 BlockStored，故它只证明引擎缓存索引公告，不单独证明 GPU 写入完成。新增事件目录将其与路由观察到的成功完成前缀相交；BlockRemoved/缺口/清空撤销确认，重放在完整结束后原子发布，禁止短暂暴露历史存储。真实 ZMQ 发布器、连续前缀、epoch/缺口、取消/读取失败等测试及原有调度相关 31 项回归已通过。在线目录消融已完成；吞吐没有显示收益，详见第 6 节。

权重量化候选已通过镜像下载：[Qwen2.5-3B-Instruct-AWQ](https://huggingface.co/Qwen/Qwen2.5-3B-Instruct-AWQ)，固定 revision `3559b226e8ce77211e2c1bd7ddfb7686fec4d6dd`；[vLLM 量化硬件表](https://docs.vllm.ai/en/stable/features/quantization/index.html)仅用于候选筛选，实际可用性以本机输出验收为准。

## 7. 恢复修复与追加复验（进行中）

### 7.1 已确认的根因与修复

LMCache 0.5.6 默认 V2 用分离 K/V 的 `[2,L,T,H*D]` 准备 CPU/中间缓冲；当前 Triton 物理格式为打包 K/V，传输 kernel 需要 `[1,L,T,H*2D]`。两者字节总数一样，不能据此判断索引语义正确。

独立于模型的逐元素 round-trip 中，V2 分离布局四项通过、打包布局四项失败；修正测试工具的多组 memory metadata 后，V3 在两种布局的八项检查全部通过，含 GPU staging/直接 CPU、整块与尾块、跳过已有前缀。原始结果见 `checks/transfer_roundtrip_v2.json`；早期工具缺 metadata 的失败也保留，不冒充引擎错误。

修复使用已有 V3 复制能力，并增加本项目的初始化顺序适配：在 CPU allocator 捕获形状前完成格式发现；打包布局若仍使用 V2 则直接报错。未改模型权重，也没有放宽 Coding 概率阈值。

`checks/cpu_prefix_fidelity_v3_long/` 的 8 个 Coding 提示和 3 个较长前缀事实提示全部通过；CPU 实际恢复 1024～2816 tokens（Coding）和 1536 tokens（事实）。事实提示新增首块内唯一 case 身份，避免共享前缀干扰；内容判断接受包含正确事实的自然语言回答。旧失败记录不删除。
