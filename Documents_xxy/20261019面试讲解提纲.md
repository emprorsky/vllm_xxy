## 1. 30 秒介绍

我研究的是共享前缀推理中“命中缓存是否就等于更快”这个问题。先在 vLLM V1 内做了缓存亲和准入、重算成本感知抢占和公平性保护，再扩展到四张 3080 Ti，分别处理实例内排序、跨实例放置和 CPU 缓存保存。新扩展没有停留在打开 APC/offload/PD 开关，而是实现了工作量与淘汰损失代理、受工作集压力控制的保存准入，以及带完成确认和事件失效的前缀目录，并用公开 Coding Agent 文本轨迹和可控热点负载验证。

这项工作借鉴 Preble 和 EfficientAgent，重点是源码适配、状态语义、消融和可复核证据，不声称发明这些论文的核心思想。

## 2. 已有能力与自己完成的边界

| 能力 | vLLM/LMCache 已有部分 | 自己的工作 |
|---|---|---|
| APC | KV 分块、前缀哈希、复用与驱逐 | 实例内准入排序、Top-W 特征和 generation 失效（原分支）；新目录对真实事件和完成状态的保守组合 |
| 本地调度 | 默认等待队列、分配、抢占和恢复流程 | cache-affinity、recompute-aware、aging；按新硬件和 PD 角色重新消融 |
| 路由 | 现有生态已有缓存/负载阈值规则 | 同目录下的六种对照、按工作量/剩余 prefill/淘汰代理评分、突发原子登记与异常释放 |
| CPU offload | LMCache 存取、复制、chunk 去重、淘汰；已有请求级 skip_save | 根据近期会话工作集与真实 resident/eviction 反馈决定何时使用 skip_save，冻结逻辑请求决定、适配生命周期 |
| PD | NIXL 数据移动与 vLLM connector | 严格 P→D 交接代理、独立角色策略、缺失元数据报错、真实传输与同资源对照 |
| 分块/量化 | 后端执行能力 | 作为控制变量评估策略敏感性，不能把打开开关本身归为新算法 |

## 3. 可以深入追问的设计

### 3.1 为什么最高缓存命中可能最慢

缓存复用只减少一部分 prefill；队列里的 decode、输入长度和未来输出预算仍决定等待。把热点始终送到一张卡，可能为了节省几百毫秒 prefill 等待数秒。反过来，只数请求数也会把 32-token 与 128-token 输出预算当成同样工作量。

当前评分是在线排序代理：排队工作 + 剩余 prefill + 可能受影响的唯一缓存片段代价。输出只用请求可见预算，不看评估轨迹的未来真实输出。系数不是精确时间模型，静态版存在批处理重叠与剩余工作未衰减误差；新增remaining版按真实输出token更新进度，memory_remaining用FIFO槽位和KV预算近似排队。后者保留同一决策同一worker的串行影子估计，分别衡量预测误差。

`work` 是队列工作与剩余 prefill 的 argmin；`cost` 只多淘汰项。threshold→work 还改变了决策规则，因此不能声称它严格只隔离负载估计这一因素。

### 3.2 为什么不一直跳过大规模 CPU 写入

没有缓存压力时，大上下文值得存；一刀切会使冷启动会话永远无法建立 CPU 副本。在积压会话工作集超出 CPU 容量、缓存接近满载且近期真的发生淘汰时，大规模回填更容易写完即被替换，小幅续写则可能延长有用前缀的寿命。

实现上将“工作集超容量”“实际接近满载”“发生容量淘汰”分别记录；后端确认的连续 CPU 前缀决定新增 chunk 数。GPU 命中不等于 CPU 已保存，不能用 GPU hit 冒充 CPU coverage。

同一请求的决定第一次解析后冻结，避免 chunked prefill 或抢占恢复时翻转。会话在工具等待期间仍进入近期工作集；决定表在完成时清理，会话表按时间窗过期。遥测陈旧时恢复正常保存，避免仅因监控失效长期拒写。

### 3.3 为什么容量指标需要源码核对

传输 pin 占比与 CPU 层真正存有多少缓存是不同口径。原型直接观察 LMCache LocalCPUBackend 的 hot cache，并在容量淘汰路径计数；不把同名 usage 百分比直接拿来做压力判断。当前依赖 LMCache 0.5.6 的私有接口，属于版本限定适配。

### 3.4 为什么 BlockStored 仍不等于可复用就绪

本分支可以在 allocation 时公告完整块哈希，GPU 尚未完成相应写入。事件目录还要求一个覆盖该输入前缀的请求由路由观察到成功完成。移除、序列缺口、清空撤销确认，重放先在私有快照内执行，再原子发布最终状态，避免把历史存储、后续已删除的块短暂暴露给路由。

这仍不是物理驻留 oracle：有事件传输延迟；事件缺少物理重复副本身份，按任一移除撤销可能低估。目录只影响选路，最终复用检查由引擎完成。

### 3.5 为什么 P 与 D 不能照搬一个评分

P 主要关心未命中输入和 prefill 队列；D 主要关心 decode 积压、有效 KV 容量和传输。将 P 的 remaining-prefill 信号直接套到 D，会把已经远端就绪的输入重新当成计算工作。

4 张消费级卡、3B 模型不一定适合 2P2D。若 D 端吞吐先饱和，额外的 P 端可能空闲；还要付出传输与完整权重副本的成本。必须与同卡数完整副本比较，不能只比较分离前后某一个阶段。

严格失败策略与返回 KV 元数据只是第一层证据，还需日志/计数器确认实际传输、D 初始 prefill 及抢占后的重算。请求完成不等于架构更优。

### 3.6 内存队列模型具体近似了什么

对每个实例维护按接收顺序排列的在途请求。每个请求预留完整私有suffix与可见最大输出预算，
共享前缀按完整块身份去重；生成过的KV不会因为剩余输出预算变小而提前释放。
在max batch槽位与扣除null block的KV预算内，模拟FIFO开始时刻；不能入场时等最早一个估计任务结束。
超过64个在途请求时回退串行总工作量，避免模型本身开销失控。

它没有精确模拟真实continuous batching，也没有物理pinned block oracle。
真实输出只更新可见剩余工作，不用等待时间猜进度、不看未来输出。入场KV估计偏保守，
实际batch服务时间仍可能不同于C=1校准。eager下有清晰收益，Graph下相对串行模型吞吐仅+0.46%，
说明排队预测误差降低也不保证可观的决策收益。预测误差用同决策同worker影子比较，避免选路不同造成混淆。

### 3.7 应该深入讲哪个修复

优先讲打包KV布局与allocator初始化顺序，其次讲已有32-token GPU前缀时2048加载上限实际新增2016。
二者都先发现强门禁失败，保留失败数据，再做字节/边界检查，最后回到模型概率与前缀事实验收。
细节见《20261019面试阅读路线.md》。简单算术或HTTP200不足以证明恢复正确。

### 3.8 为什么小KV池的L收益反而不明显

亲和调度需要候选中存在值得复用、仍可访问的前缀。8192-token池过小时前缀普遍被挤掉，
仅重新排序不能创造缓存；自然容量组有更大的可复用空间，观察到命中率上升与吞吐收益。
AWQ进一步扩大自然KV容量后，默认策略已能保留更多前缀，L的新增吞吐收益又收窄。
这是本组结果支持的解释，不等于“显存越大收益越高”的普遍规律。
O解决的是另一层的写入/容量周转成本，容量充足时过滤反而没有必要。

公开轨迹当前固定64输出预算，避免工作量差异污染服务对照；半合成机制组补32/64/128混合预算。
这仍不足以代表真实Agent完整输出分布，后续应补原始输出长度和到达时间驱动的回放及真实工具闭环。

## 4. 实验结果如何讲才可信

- 原单卡结果与本次 3080 Ti/3B 结果分开，不跨硬件拼提升。
- 本次先固定 8192-token GPU KV 构造压力，再补自然显存容量对照，明确人工限容边界。
- offload 三种准入必须固定 GPU/CPU 容量、驻留请求上限、去重与复制路径。
- 决赛对照做至少三轮独立交错运行，展示每轮值；不能拿单轮 P99 宣称稳定收益。
- 公开 Agent 轨迹保留历史输入文本与调用顺序，但不执行工具、也不评价任务修复率；不能叫完整在线 Agent benchmark。
- 真实轨迹经 4K 长度过滤后偏向早期短调用；热门前缀负载是半合成机制实验，两者分开报告。
- 固定输出预算并忽略 EOS 是服务压力实验，不能替代非强制输出的质量检查。
- 当前基本正确性通过 native RMSNorm/Triton 路径，默认预编译算子异常仍是本机限制；不能将工作配置性能代表健康默认 CUDA 路径。
