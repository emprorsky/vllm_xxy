原项目已验证范围是 AutoDL 单张 RTX 4090、Qwen2.5-7B，主要工作包括：

1. 在用户优先级、有限 Top-W 窗口及 aging 约束下，利用恢复状态、已有前缀和剩余上下文计算量进行准入重排。
2. 在运行请求 KV 分配失败时，利用恢复状态和重算成本代理选择抢占对象。
3. 以只读查询、懒加载和本地 generation 失效机制降低特征查询开销。

原材料中的代表结果：16 类共享前缀、1250 KV blocks 等指定压力条件下，输出吞吐提高约 4.20%，总耗时降低约 4.00%，TTFT P99 降低约 2.24%，TPOT P99 降低约 15.43%。同时存在 ITL P99 回退以及容量变化后的负结果。

这些数字是既有材料记载，本次对话没有重新执行验证。它们不能直接外推为多实例、offload 或 PD 下的收益。

原代码还存在需要保留的语义边界：

- Waiting 请求准入时 KV 分配失败，不等于立即抢占 running 请求；原材料描述的路径会停止本轮准入。
- Running 请求可能处于 decode，也可能继续执行 prefill chunk；两者续算申请 KV 时都可能触发抢占。
- Top-W 负责 waiting 阶段的候选选择，不等于对每个 running chunk 都重新排序。
- Aging 提供排序上的等待保护，不会凭空增加资源，也不能直接保证跨实例端到端公平性。

## 3. 面试官思路与原项目如何融合

### 3.1 建议的项目主线

建议定位为：**面向 Agent / Coding 共享前缀负载的多实例 KV 感知调度优化**。

业务背景是系统提示、工具定义、代码上下文和对话历史带来前缀复用，但请求热度、输入输出长度和活跃会话规模不同，使缓存位置、计算负载、显存容量与执行顺序出现不匹配。

前缀复用要求实际 token 序列开头一致。相同仓库或相似语义不保证前缀命中；代码更新、模板变化和历史截断都可能改变可复用范围。

| 层面 | 遇到的问题 | 对应方法 | 需要付出的代价 |
|---|---|---|---|
| 请求放置 | 轮询错过缓存；纯缓存亲和造成热点 | 缓存与负载联合路由 | 元数据维护、估计误差和热点控制 |
| 缓存保留 | GPU 淘汰后仍有复用价值的前缀 | CPU KV offload，后续可扩到 SSD | 保存、加载、带宽和存储开销 |
| 实例内执行 | 命中后仍排队、争抢 KV 或反复恢复 | 原有准入、aging、恢复成本感知抢占 | 热路径开销、冷请求等待和策略适用边界 |

可用的一条叙事链是：**请求送到合适实例，值得保留的 KV 能留住，进入实例后按合理顺序执行和恢复。**

### 3.2 不把现成系统能力包装成个人创新

vLLM 相关路由组件和 KV 后端已有缓存感知路由、负载感知及 offload 能力。接入与配置可以作为工程工作，个人增量需要通过对照实验说明。

最贴近现有项目的增量问题是：

> 已经启用缓存与负载联合路由、CPU offload 后，本地准入和抢占是否仍有额外收益？收益出现在哪里，又在什么条件下失效？

若进一步提出新规则，应针对测得的瓶颈：

- 只用请求数量不能反映长短请求的实际工作量。
- 缓存目录认为有 KV，实际可能已驱逐、正在加载或来源实例已重启。
- CPU 命中不代表加载一定比短段重算更快。
- 原来的剩余补算 token 信号，加入外部 KV 后可能不再准确。

候选成本模型可以考虑预计排队、KV 加载与剩余 prefill 的关键路径、显存和恢复风险。它首先是待验证的决策模型，不是精确预测公式；加载与计算可能重叠，也可能只复用部分前缀。

第一版可以使用长度分桶、历史统计、滑动平均等低开销方法，不必在面试前仓促构建复杂预测系统。

### 3.3 Offload 没有自动消除抢占问题

本次检查到，本地 native offload 路径的 offload_prompt_only 默认值为 True；官方文档同样说明该配置跳过 decode blocks。因此不能假设活跃请求的全部生成历史均已在 CPU 备份。

需要区分：

1. GPU 已有且可使用。
2. CPU 中存在已完成保存的副本。
3. 已发起加载但尚未就绪。
4. 没有可复用副本，必须重算。

抢占时还需考虑共享引用、延迟释放以及能够立即回收的物理 KV 空间。CPU 容量增加不等于活跃请求可以无限增长。

### 3.4 当前可用的面试叙述

> 我研究的是共享前缀负载下，KV 缓存怎样转化为实际服务收益。多实例中，请求可能错过已有缓存，也可能因为亲和路由而集中到热点；有限显存又会带来缓存淘汰、运行请求抢占和恢复开销。
>
> 我已完成的是实例内的缓存感知准入与恢复成本感知抢占，在优先级、有限窗口和 aging 约束下减少补算与恢复成本。原单卡指定压力负载中观察到约 4.2% 的输出吞吐提升，同时也记录了尾延迟和容量外推的负结果。
>
> 接下来用多实例路由、CPU offload 和 PD 架构做独立对照，验证本地策略的额外价值，并根据缓存层级、传输就绪和恢复方式调整成本信号。目标是满足延迟约束的有效吞吐，不只追求命中率。

只有后续真实完成并复核的实验，才替换最后一段中的计划性表述。

## 4. GPU 数量、并行方式与 PD 的区别

以下假设每个完整服务实例单卡能装下模型、TP=1，每个实例独占一张 GPU：

| 实验 | 最少 GPU 数 | 能回答的问题 |
|---|---:|---|
| Chunked prefill 与原策略 | 1 | 不同预算下的本地策略适用性 |
| CPU KV offload | 1 | 加载代替部分重算后的效果 |
| 两个完整副本与路由 | 2 | 缓存位置与负载均衡 |
| 1P1D | 2 | 分离、交接和两端本地调度 |
| 2P1D | 3 | 多 P 的缓存复用与排队权衡 |
| 1P2D | 3 | 多 D 的负载与容量选择 |
| 2P2D | 4 | 两端均有实例选择空间 |

TP=2 通常是一份模型的两个协同执行 rank，不是两个可以独立选路的完整副本。

1P1D 本身没有同角色多实例选路空间。1P2D 虽然有 D 端选择，但不能因此声称验证了 P 端缓存亲和路由。对多轮请求，送回同一个 D 也不会自动让 P 少算；还需要实际实现状态跟踪和相应 KV 复用流程。

PD 不是所有 Agent / Coding 流量的必选架构。它有助于阶段隔离和独立扩容，但收益受模型、流量、缓存复用、硬件及传输成本影响，需要与同资源预算的聚合部署比较。

## 5. 实验顺序在对话中的调整

### 5.1 最初方案

最初建议单卡 chunking / offload，随后双完整副本路由，再做 1P1D，最后多 P、多 D。该安排有利于逐步归因。

### 5.2 用户提出生产 PD 架构质疑后的修订

用户担心面试官会质疑：这类场景通常采用 PD，只做非 PD 是否缺乏意义。

最终调整为：**不要求先完成所有非 PD 组合，把最小 PD 验证提前。**

非 PD 作为机制参照；PD 用于验证架构适用性。若目标团队实际部署 PD，应承认非 PD 证据不足以证明其生产架构收益。

PD 后原策略需要重新检查：

| 原机制 | PD 下的变化 |
|---|---|
| 剩余 prefill 感知准入 | P 端仍可能适用；D 端大量上下文来自远端时，该信号可能缺少区分度 |
| 恢复成本感知抢占 | 需考虑保留、重传、外部加载或重算等实际恢复方式 |
| 本地 generation | 不能代替跨实例目录与传输状态的一致性管理 |
| Aging | 本地保护不等于跨 P/D 的全局公平性保证 |

### 5.3 面试前的最终优先级

1. 环境恢复、单卡推理、四卡可见性和正确性。
2. 尽早进行 1P1D 的真实 KV 传输验证。
3. 在 1P1D 下比较默认、只改 P、只改 D、两端均改。
4. 按测得瓶颈选择 2P1D 或 1P2D，再考虑 2P2D。
5. 做多完整副本的缓存路由与本地策略增量。
6. 加入一种 CPU offload 后端，验证加载是否真正触发，再比较策略增量。
7. 重复关键结果、保留负结果、整理面试讲述。

具体顺序可根据环境和失败原因调整。PD 与 offload 的复杂组合、SSD、多模型泛化及大规模参数扫描，不作为今晚必须完成项。

对环境和传输排错设置约 60～90 分钟的初始时间预算。如果某条路径持续不通，及时记录阻塞并切换可交付实验，不把整晚消耗在驱动或宿主机改造上。该时间是工作安排，不是完成保证。

## 6. 对照实验与评价设计

### 6.1 PD 核心消融

| 组别 | P 端 | D 端 |
|---|---|---|
| A | 默认策略 | 默认策略 |
| B | 修改策略 | 默认策略 |
| C | 默认策略 | 修改策略 |
| D | 修改策略 | 修改策略 |

先检查策略是否被触发、是否改变决策，再解释延迟和吞吐。如果 D 端原信号失效，应保留该负结果，之后按实际问题适配。

### 6.2 多副本路由基线

- Round-robin。
- 负载优先。
- 纯前缀亲和。
- 现成缓存与负载联合路由。
- 若实现新模型，再与较强的现成联合策略比较。

不能只优于轮询，就声称优于已有缓存感知路由。

缓存目录第一版允许明确标注为近似推测。若通过 KV events 维护实际位置，还需要处理驱逐、重启、事件缺失和元数据陈旧，不能默认目录完全准确。

### 6.3 路由、offload、本地策略的八组矩阵

这是可补充的完整组合，不再是开展 PD 的前置条件：

| 组别 | 缓存＋负载联合路由 R | CPU offload O | 修改本地策略 L |
|---|---|---|---|
| 000 | 关 | 关 | 关 |
| 100 | 开 | 关 | 关 |
| 010 | 关 | 开 | 关 |
| 001 | 关 | 关 | 开 |
| 110 | 开 | 开 | 关 |
| 101 | 开 | 关 | 开 |
| 011 | 关 | 开 | 开 |
| 111 | 开 | 开 | 开 |

R 关仍使用预先固定的负载优先路由，各组硬件数量相同。最关键的比较之一是 110 对 111，检验已有系统能力之外，本地策略的增量。

在代表性场景中，再拆分默认、只改准入、只改抢占和两者都改，避免混淆贡献。

### 6.4 Offload 机制验证

构造前缀集合 A 被访问、随后被其他前缀挤出 GPU、最后 A 再次出现的序列。检查实际 GPU miss、CPU hit、加载字节、重算 token 和时延。

工作集需要能够形成 GPU 缓存压力，并与 CPU 缓存容量相匹配。只开启配置、不出现有效加载，不能证明 offload 有价值。

先使用按实例隔离的 CPU 缓存。跨实例共享 CPU KV 是后续独立变量，同机进程不会自动共享缓存。

### 6.5 负载、指标与重复

建议覆盖：均匀共享前缀、热门前缀倾斜、热点切换、旧前缀重现、长短输入输出混合及低复用请求。调参与评估使用不同前缀集合或流量序列。

主要评价目标为满足指定延迟约束的 goodput，可报告成功且满足约束的请求数/秒，以及这些请求的输出 token/s。实验中的延迟目标称为 SLO；不能仅凭命中率或吞吐变化就宣称达成生产 SLA。

同时记录：

- TTFT、TPOT、ITL 及其明确的统计口径。
- 吞吐、错误、超时、各类请求等待和公平性。
- 各实例排队、KV 层级命中、实际加载和重算。
- 抢占、恢复成本、改选 victim 次数及准入策略激活情况。
- Router、本地查询和调度本身的开销。
- CPU、内存、PCIe、磁盘等共享资源竞争。

采用相同到达轨迹、固定预热及缓存初始化条件，交错运行并独立重复。正式 P99 结论需要比原 192 请求实验更充分的样本。跨架构比较要固定资源预算，如 1P2D 对三副本、2P2D 对四副本。

## 7. 平台选择讨论

### 7.1 AutoDL

同机单实例多卡适合当前短期实验：可以启动多个 vLLM 进程、Router 和本机压测程序，通过 localhost 通信。应用层路由通常不需要宿主机路由表或 Kubernetes 权限。

普通容器内不支持再运行 Docker；宿主机驱动、内核、硬件 P2P 等不能按容器 root 权限推定可修改。个人用户对外访问服务可使用 SSH 隧道，但正式压测优先在服务器本地进行。

官方说明目前不再通过开通内网 IP 支持普通实例的多机多卡并行，因此不建议临时用几个不相关单卡容器经公网拼 PD。

### 7.2 阿里云与腾讯云

本次核对的官方标准 GPU 云服务器规格中，没有列出 RTX 4090。两家有 A10、A100、V100、T4 等规格，具体库存、报价和地域需账户控制台确认。第三方市场或商务定制不等同于官方标准实例。

推荐两家的理由原本是自管系统、Docker、VPC、安全组和服务编排的控制程度，不是因为提供 4090。

A10 即使与 4090 同为 24GB 显存，也不代表性能相同。换硬件后必须重建默认/修改策略对照。root 权限同样不能保证底层 GPU 互联或 RDMA 能力；这些取决于具体实例和网络配置。

在现有环境可用且面试时间紧张的条件下，优先复用 AutoDL，避免为平台迁移增加变量。

### 8.1 模型改为 Qwen2.5-3B-Instruct

用户接受换更小模型。建议主实验使用 Qwen2.5-3B-Instruct，保持同系列和 BF16，权重粗估约 6.2GB；12GB GPU 是否足以支持指定上下文、并发和后端缓冲，以实际启动 profiling 为准。

建议的保守起点，均为待测配置：

| 参数 | 起点 |
|---|---|
| 模型 | Qwen/Qwen2.5-3B-Instruct |
| 精度 | BF16 |
| TP | 1 |
| 最大上下文 | 4096，输入与输出合计 |
| max_num_seqs | 16 |
| max_num_batched_tokens | 1024 |
| APC | 开启 |
| Chunked prefill | 开启 |
| CPU offload | 基础实验通过后，每实例先配 4～8GiB |

1.5B 可作为排错备用，不预先作为主模型。先不加入量化，以减少变量。

原 4090＋7B 结果与新 3080 Ti＋3B 结果是两组独立证据。新实验必须在相同新硬件、模型和负载上比较策略，不能直接用旧吞吐做对照，也不能照搬旧 1250-block 容量作为已知最佳压力点。

### 8.2 通信与兼容性

3080 Ti 没有 NVLink。没有 NVLink 本身不等于所有传输都不能运行，也不能保证 NIXL 可用。需要检查 GPU 拓扑、实际 peer-access、connector 路径及输出正确性。

4090 与 3080 Ti 计算架构不同。原预编译依赖可能兼容，但只针对 4090 编译的扩展可能需要补编译；先检查，不能先假设必须重装或全部可直接复用。

如果只能经 CPU 中转，需明确记录。该路径的性能结论不能代表高速 GPU 互联上的 PD。

## 9. 同一四卡实例共享与独立的资源

| 资源 | 实例内的关系 |
|---|---|
| GPU 计算与显存 | 每卡独立，每卡 12GB；多副本时不自动拼成 48GB |
| CPU 配额 | 四卡合计后由进程共同使用，不自动为每 worker 固定绑核 |
| CPU 内存 | 实例总配额共同消耗，不自动按 worker 各限制 30GB |
| 系统盘和数据盘 | 同一文件系统与容量 |
| 软件环境 | 可共用 conda、Python 和依赖 |
| 网络与端口 | 同一实例内可用 localhost，服务端口需区分 |
| /dev/shm | 共享实例的空间与限制，不是额外无限内存 |

共享 CPU 内存不等于自动共享模型对象或 CPU KV。模型权重文件可以只下载一份，但 TP=1 的各 GPU 引擎分别加载权重，各自管理 Scheduler、队列和 GPU KV。

若四个实例各配置 8GiB CPU KV，则总计约 32GiB，另外还要给加载峰值和其他进程留内存。不能让每个进程都按拥有整个 120GB 实例配额来配置。

租到的 GPU 对实例独占，但不等于独占整台八卡宿主机。主机内存带宽、PCIe 上游和磁盘 I/O 可能产生竞争；公网带宽按 AutoDL 官方说明是共享方式。四个 worker 同时 offload 可能受共同传输瓶颈限制。

## 10. 镜像、克隆与数据盘迁移

讨论过程中的结论：

1. 优先复用原单卡 4090 的系统盘镜像，保留 conda、Python、PyTorch 及依赖。
2. 镜像只包含系统盘。原 /root/autodl-tmp 中的源码、wheel、模型和实验结果需要另外迁移。
3. 同地区可使用克隆实例，并勾选同时拷贝数据盘；系统盘克隆完成后再拷贝数据盘。
4. 跨地区按系统盘镜像＋数据盘传输处理，实际耗时受网络和文件数量影响。

用户随后确认系统盘镜像已复用，因此当前最直接的下一步是复制原实例的数据盘，而不是重复创建另一套环境。

复制时确认：

- 源是原单卡 4090，目标是新四卡实例。
- 保留 /root/autodl-tmp 的目录结构，尤其可编辑安装引用的源码路径。
- 目标磁盘容量足够，不误覆盖新实例重要内容。
- 等复制结束后才测试导入和推理。
- 原实例先保留，避免迁移和新 GPU 兼容性问题失去回退条件。

## 11. Windows Codex 如何操作 AutoDL

用户原来在 AutoDL 使用 Codex CLI，希望改为在 Windows Codex 客户端交互，在容器里修改代码、配置环境和执行实验。

### 11.1 两种连接方式

| 方式 | 原理 | 远端是否需要 Codex |
|---|---|---|
| 客户端内置远程项目 | Windows 界面经 SSH 启动和连接远端 Codex 后端，由远端工具进程操作文件与命令 | 需要安装并认证，登录 shell 能找到 codex |
| 当前聊天调用普通 SSH | 当前聊天通过本机命令工具执行 ssh/scp，在远端读写文件、运行脚本并回传输出 | 普通 SSH 操作不需要远端 Codex CLI |

官方远程项目文档给出的入口为 Settings → Connections → SSH，并从本机 SSH config 中发现具体主机别名。用户当前没有找到该入口；本次没有确认界面缺失的具体原因，也没有通过修改客户端内部数据库或隐藏设置绕过功能开关。

为减少面试前的环境折腾，计划先采用当前聊天通过 Windows OpenSSH 操作远端的方式。

本次已只读确认本机存在：

- Windows OpenSSH 的 ssh、ssh-keygen、scp。
- C:/Users/xxy/.ssh/config。
- 已有 id_ed25519 与对应公钥文件。

没有读取私钥内容，没有新增主机配置，没有测试 AutoDL 登录。

### 11.2 为什么 Codex 可以修改容器代码

权限链条是：用户授权工作 → 本机工具发起 SSH → 服务器验证登录身份 → 远端账户按文件权限执行修改。

普通 SSH 方式可由远端命令应用补丁、运行文件编辑脚本，或者通过 scp 上传文件。文件修改依赖实际登录账户的权限；容器 root 通常能修改容器项目，但不是宿主机管理员。

密钥认证使用本机私钥完成签名验证，不需要把私钥发给模型或服务器。用户只需要提供新实例的 SSH 连接命令或别名，不需要把密码或私钥贴进聊天。

### 11.3 接通后的计划步骤

1. 获取新实例 SSH 地址、端口与用户名。
2. 检查已有 SSH 配置，按实际需要添加新别名，保留旧配置。
3. 验证连接；需要密码时，由用户在自己的终端完成一次性登录和公钥配置。
4. 确认密钥登录以及口令/agent 状态，避免夜间反复等待输入。
5. 检查 GPU、源码目录、原 conda 环境和依赖。
6. 运行单卡推理和 PD 传输验收。
7. 通过远端 tmux 或任务脚本管理长实验，记录超时、错误、命令和结果。

普通 SSH 不会自动把当前聊天变成原生远端项目，也不会自动同步容器代码到 Windows。需要查看的报告、日志和修改，应显式回传。

### 11.4 夜间运行条件

用户可以离开，但本地执行入口需要保持开机、联网、Codex 可运行，并事先完成必要连接与操作授权。

远端 tmux/任务脚本可以在 SSH 断开后继续执行已启动程序；这不等于本地电脑休眠或客户端关闭后，Codex 仍能持续主动排错。

如需后续定时检查或自动唤醒，应另行按实际实例、任务和预算配置；本次没有创建自动化、计划任务或监控。
