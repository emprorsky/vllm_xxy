## 0. 执行摘要

### 0.1 要完成的项目主线

**面向 Coding Agent / RAG 的共享前缀和多轮交互负载，联合研究请求放置、CPU KV 缓存准入及实例内执行顺序。**

三个问题依次为：

1. 请求送到哪个实例，才能兼顾缓存复用、排队和缓存淘汰代价？
2. CPU 容量有限时，哪些 KV 写入能够存活到下一次复用，哪些写入只会造成抖动？
3. 已有路由和外部缓存后，原来的准入、aging 与恢复成本感知抢占还有多少增量？

核心目标是取得能复核、能解释、能用于面试的证据。不预设三个模块均有正收益，不预设 PD 优于聚合部署。

### 0.2 最终确定的改造方向

| 层次 | 主要借鉴 | 必须落实的个人工作 | 优先级 |
|---|---|---|---|
| 多实例路由 R | Preble 的缓存复用、计算负载与淘汰代价联合决策 | 当前版本的前缀目录、工作量估计、在途登记、成本评分和独立消融 | P0 |
| CPU KV 管理 O | EfficientAgent 的工作集压力感知写入准入 | 当前 LMCache 接口适配、按实例工作集估计、CPU 容量/淘汰观测、请求生命周期一致性 | P0 |
| 实例内调度 L | 已有 Top-W、aging、recompute/reclaimable-aware 策略 | 新硬件下重建对照，验证与 R/O 的增量；按证据决定外部状态适配 | P0 验证，P1 扩展 |
| PD 架构 | 现有 connector 与代理能力 | 真实传输验收，P/D 两端消融，条件满足后验证 2P2D | P0 早期验收，P1 扩展 |
| Chunked Prefill 变量 C | 现有分块调度与 token budget | 验证分块粒度与 R/O/L、P/D 角色的交互，必要时重标定成本模型 | P1，优先于量化 |
| 量化变量 V | 已有权重量化或 KV 量化路径 | 分离计算、缓存容量与数值质量变化，验证策略可迁移性 | P2，兼容与时间允许时做 |
| 周期性前缀放置 | CacheRoute | 稳定候选实例集合、按历史热度规划、热点变化时重规划 | P2 备选路线 |
| SSD / 远端 KV | 多级缓存系统已有能力 | 需要额外存储、传输与策略对照 | P2，今晚不作为必达项 |

P0 为面试前优先交付；P1 通过前置验收且时间充足时完成；P2 不得挤占 P0 的实现、复验和结果整理时间。

### 0.3 推荐顺序

**环境与数据 → 单卡基线 → 早期 1P1D 传输验收 → 单卡 offload 改造 → 双完整副本路由 → R/O/L 组合 → PD 消融与 2P2D → 复验和面试整理。**

这里有两条并行于逻辑上的依赖链，而非要求同时运行争用资源的压测：

- 单卡与双副本负责获得三层策略的可归因证据。
- 1P1D 尽早验证技术路径，避免到最后才发现 connector 不可用。

必达交付为“双完整副本中三层形成闭环，并有明确消融”。2P2D 是通过验收后的重点扩展，不能以四个进程启动成功代替架构实验。

## 2. 研究问题与可证伪假设

| 编号 | 假设 | 必须观察的机制 | 可能使其失效的条件 |
|---|---|---|---|
| H-R1 | 工作量估计优于请求计数 | 相同请求数下区分长 prefill 与短 decode，改变选路并改善排队 | 请求长度接近、负载低、估计误差大 |
| H-R2 | 加入淘汰代价能减少后续重算 | 避开高价值前缀受损的放置，后续 miss/recompute 减少 | GPU 容量充足、热度快速变化、代价代理不准 |
| H-R3 | GPU/CPU 层级信息改善选路 | CPU 命中扣除加载成本，实际选路优于统一命中奖励 | 加载成本很小、目录不可靠、CPU 缓存可跨实例共享 |
| H-O1 | CPU 工作集不足时，限制大规模回填可减少缓存抖动 | 写入后未读即淘汰减少，实际恢复增加或重算下降 | 所有会话都很冷，过滤伤害新会话成长 |
| H-O2 | 容量足够时恢复全量保存优于始终过滤 | 条件化策略解除过滤，恢复本来可利用的命中 | 压力估计滞后、容量信号口径错误 |
| H-L1 | R/O 之后本地调度仍有增量 | 准入/victim 改变，恢复开销或排队改善 | offload 消除了大部分原瓶颈、D 端信号缺少区分度 |
| H-PD1 | 策略在 PD 中存在角色差异 | P 与 D 的触发率、排队、恢复方式不同 | 负载没有压力、KV 交接主导且调度不能改变 |
| H-X1 | 路由与 CPU 准入存在协同或冲突 | 实例会话分布改变局部工作集及存活率 | 单层收益已饱和，模块反馈导致振荡 |

“没有策略触发”“样本不足”“实现开销抵消收益”“出现稳定负收益”均可成为有效结论，但应区分原因。

## 3. 论文借鉴、已有能力与个人贡献边界

### 3.1 Preble：路由侧主参考

- 论文：[Preble: Efficient Distributed Prompt Scheduling for LLM Serving](https://arxiv.org/html/2407.00023v2)。
- 作者代码：[WukLab/preble](https://github.com/WukLab/preble)。
- 借鉴范围：全局前缀视图、复用与探索选择、将计算负载/新请求成本/潜在淘汰损失统一比较。
- 本次取舍：先适配低开销成本模型和状态维护；不承诺完整复现其 E²、自动扩展和全部本地队列机制。
- 本文拟议评分是工程适配方案，不等同于论文原始算法；论文结果不能直接转写成项目结果。

### 3.2 EfficientAgent：CPU offload 侧主参考

- 论文：[EfficientAgent: What Makes KV Cache Offloading Work for Concurrent Agents?](https://arxiv.org/abs/2609.33762)，2026-09-27。
- 作者代码：[KunmingSHAO/efficientagent_release](https://github.com/KunmingSHAO/efficientagent_release)。
- 借鉴范围：复用工作集、容量压力条件化写入准入，以及依赖保持的多轮回放。
- 核心问题：KV 必须存活到下一次使用，单看“加载比重算便宜”不足以保证收益。
- 本次取舍：适配条件化写入准入和必要观测，不照搬作者旧栈，也不预设完成完整栈距离预测器。
- 作者公开栈为 vLLM 0.13.0 / LMCache 0.3.12；本机版本不同，源码接口与生命周期必须重新核验。

### 3.4 哪些能力已经存在

|---|---|---|

## 4. 系统边界与部署形态

### 4.1 缓存层级命名

本文使用 GPU / CPU / SSD 的物理位置描述，必要时约定 GPU 为第一级、CPU 为第二级、SSD/远端为第三级。

LMCache 自身的 L1/L2 命名可能指其内部存储层，不一定与上述命名一致。日志、图表和配置必须写清物理位置，不直接混用名称。

扩大 CPU 缓存池不等于扩大 GPU 可执行显存；活跃请求仍需 GPU KV、加载缓冲和调度资源。同机进程也不会自动共享 CPU KV。

### 4.2 实验形态

| 形态 | GPU 数 | 结构 | 主要回答的问题 |
|---|---:|---|---|
| 单卡聚合服务 | 1 | 一个完整模型实例，TP=1 | O 的机制、L 的增量、chunking 影响 |
| 双完整副本 | 2 | 两个独立 TP=1 引擎，由 Router 分发 | R 的独立贡献与 R/O/L 组合 |
| 1P1D | 2 | 一个 P、一个 D，各 TP=1 | 真正 KV 传输、P/D 角色差异与策略适配 |
| 2P1D / 1P2D | 3 | 按已观察到的 P 或 D 瓶颈扩展 | 角色资源比例与同角色选路 |
| 2P2D | 4 | 两个 P、两个 D，各 TP=1 | 两端选路、P/D 策略消融、四卡架构对照 |
| 四完整副本 | 4 | 四个独立 TP=1 引擎 | 2P2D 的同 GPU 数聚合部署参照 |

双完整副本不是 TP=2；1P1D 没有同角色选路空间；D 的会话黏性不自动使 P 少算。

### 4.3 资源控制

- 每 GPU 一个主要引擎；同卡不并跑两套正式性能实验。
- Router、client、引擎、LMCache 的 CPU、RSS、线程数与亲和设置写入 run manifest。
- 初期使用按实例隔离的 CPU 缓存；共享 CPU KV 作为后续独立变量。
- 各实例 CPU 缓存合计、模型加载峰值、pinned memory、`/dev/shm` 留足 120 GiB 额度内的余量。
- 2P2D 的 GPU 对应关系固定；实测每种跨 NUMA 路径，不能把拓扑变化误认作策略收益。
- 不为提升指标临时更改某个对照组的 GPU KV 容量或传输路径。

## 5. 负载与数据设计

### 5.1 三类数据，各自独立标注

1. **公开 Coding Agent 轨迹回放**：优先选含模型请求、工具观察、代码、测试日志的 SWE-agent / mini-SWE-agent / OpenHands 公开轨迹。
2. **可控机制负载**：控制共享前缀、访问次序、热点和会话并发，用于证明机制。
3. **少量闭环会话**：本次生成的回答进入下一轮历史，用于检查实际多轮缓存路径。

公开轨迹入口：[SWE-bench/experiments](https://github.com/SWE-bench/experiments)。先选具体可下载的提交/仓库及其许可，不假设所有 leaderboard 条目均提供完整轨迹。

若 20～30 分钟内不能取得可用样本，先用公开可得代码文本构造明确标注的机制负载，同时保留真实轨迹获取任务。不得把构造负载称为生产流量。

### 5.2 数据准备与规模

- 初始候选：30～50 个会话，每个选 4～8 次模型调用；只是试跑起点，不是最低统计样本要求。
- 先统计实际输入长度、输出长度、会话间隔、工具等待、稳定前缀长度和共享结构。
- 调参会话与正式评估会话按 task/session 划分，避免同会话泄漏到两边。
- 保留原始轨迹、来源 commit、原记录索引及转换脚本的对应关系。
- 不使用未来的输出长度、下一次访问或后续热点信息做在线决策。
- 提示词按当前模型 tokenizer 和 chat template 重新构造；原模型 token ID 不能未经验证直接送给新模型。
- 超出上下文的样本优先过滤或选自然较短片段，报告覆盖率；若截断，报告截断比例、位置及共享结构变化。
- 禁止为了增大命中率，静默把所有请求重排成“共享代码在前、任务在后”。若测试这种模板调整，应单独标注为独立变量。

### 5.4 依赖与输出控制

- 会话内下一轮不得早于上一轮完成及其工具等待；会话之间可以交错。
- 固定轨迹回放保持请求内容和输出工作量尽量一致，调度可以改变后续到达时刻。
- 强制历史输出 token 可用于受控回放，但会影响 logits 路径和开销；所有对照使用同一种机制，单独做非强制 greedy 正确性抽查。
- 若只固定输出预算而不强制输出，记录实际 token 数差异，不能仅按墙钟时间比较。
- 固定轨迹历史回答和本次生成不同的实验，应标为固定回放，不能当成真实闭环对话。
- 开环固定到达用于路由过载对照；依赖保持的闭环回放用于 Agent 会话完成时间。两类结果分开报告。

### 5.5 负载组

| ID | 结构 | 主要验证 |
|---|---|---|
| W0 | 低共享、低压力 | 策略额外开销和无收益边界 |
| W1 | 多组稳定共享前缀、均匀访问 | 正常缓存复用与基线 |
| W2 | 热门前缀倾斜、长短请求混合 | 阈值路由与工作量估计 |
| W3 | 热点由 A 迁移到 B | 路由估计滞后、目录陈旧、重平衡 |
| W4 | A 热身 → 其他前缀施压 → A 重访 | GPU miss、CPU hit、实际恢复 |
| W5 | 多轮会话增长并夹杂工具等待 | 复用工作集、CPU 写入抖动 |
| W6 | 早期历史改写/摘要、会话结束后不再访问 | 精确前缀失效与陈旧缓存边界 |

正式对照优先 W2、W5 两类，再从 W0/W3/W4 中选择最能解释机制的一类。避免每种策略与全部负载做笛卡尔积。

## 6. 模型、Chunked Prefill 与量化变量

### 6.1 主实验基线

主模型拟用 `Qwen/Qwen2.5-3B-Instruct`，BF16、TP=1。备用小模型只用于排错，换模型后必须重新记录配置并重建性能对照。

| 参数 | 保守起点 | 调整原则 |
|---|---|---|
| 最大上下文 | 4096，输入输出合计 | 若轨迹保留率低且显存允许，再试 8192；组间固定 |
| `max_num_seqs` | 16 | 与活跃会话池分开配置；按 profiling 调整 |
| `max_num_batched_tokens` | 1024 | 先追加 512/2048 中一个对照，具体分层设计见 6.2 |
| APC | 开 | 关闭 APC 仅作指定机制对照 |
| Chunked prefill | 开 | 作为 P1 显式变量；主 R/O/L 对照内固定，另做交互实验 |
| CUDA graph / eager | 先选兼容设置验收 | 正式比较保持相同；若必须 eager，则全组一致 |
| GPU KV 容量 | 先记录自然容量 | 可设置人工压力档，但需明确标注并保留自然容量结果 |
| CPU KV 容量 | 由工作集试测决定 | 设不足/临界/充足三档，不直接照搬 4～8 GiB |
| 量化 | 基线为 BF16 权重与模型默认 KV dtype | P2 先选一种兼容的权重量化，KV 量化单独验收，见 6.3 |

模型 revision、文件完整性、tokenizer/template、KV dtype、块大小、attention backend、graph 模式及启动命令必须留存。旧 4090+7B 的 1250 blocks 不是新环境最佳压力点。

### 6.2 C：Chunked Prefill 的粒度与开关

**目的：研究已有调度策略对执行粒度的敏感性，并检查 R/O 的模型在粒度变化后是否仍成立。** 开启 chunking 本身是框架能力，个人贡献应来自交互分析、状态适配或经验证的进一步调度改造。

当前分支的 `enable_chunked_prefill` 控制是否允许切分，`max_num_batched_tokens` 是每轮总 token 预算，包含 decode 等已调度工作；它并不等于每个 prefill 请求固定获得的 chunk 大小。实际分块还受其他请求和调度约束影响，必须记录每轮实际 prefill tokens 与请求跨轮次数。

| 配置 ID | `enable_chunked_prefill` | token budget 起点 | 用途 |
|---|---|---:|---|
| C-MAIN | true | 1024 | 主实验起点 |
| C-SMALL | true | 512 | 较细粒度，考察调度/查询频次与 decode 干扰 |
| C-LARGE | true | 2048 | 较粗粒度，考察 prefill 进展、KV 增长与等待 |
| C-MATCH-ON | true | 不小于 `max_model_len` 的同一预算 | 与关闭配置作预算匹配对照 |
| C-MATCH-OFF | false | 与 C-MATCH-ON 相同 | 观察禁止切分的效果与适用边界 |

先在 C-MAIN 与 C-SMALL/C-LARGE 中选一个差异明显的配置。预算匹配开关实验为追加项：当前配置校验要求关闭 chunking 时 `max_num_batched_tokens >= max_model_len`；不能将关闭+大预算与开启+小预算直接描述为“只改变开关”。具体校验与 backend 要求以实际版本为准。

较大预算可能提高峰值激活/临时缓冲占用，必须重新 profiling。若 12GB 单卡启动失败或 connector 要求分块，记录该限制，跳过该组合，不通过额外缩短上下文或降低并发掩盖不可比配置。预算匹配时，开启配置也可能未真正发生切分；应以实际分块率解释无差异结果。

需要检验的四类交互：

1. **C×L：** 小 chunk 增加调度轮数，Top-W 特征查询、aging 和抢占的机会可能变化。比较策略触发次数、每轮开销、恢复重算与 ITL，不能只看吞吐。
2. **C×O：** prefill 分块改变 CPU KV 保存时机、完整 chunk 对齐及加载等待。GPU 调度 chunk、GPU KV block、LMCache 存储 chunk 是不同概念，不要求大小相等；但需遵守选定 backend 的对齐约束。重复 lookup/分块不得重复计入活跃会话，也不得反复改变写入决定。
3. **C×R：** prefill 服务时间和 decode 竞争改变后，重新校准工作量估计。比较固定旧模型与重标定模型时应明确区分，不把模型失配误认为路由思想无效。
4. **C×PD：** 先改变 P 端 budget，D 端和传输设置固定；只有 D 端确有本地 prefill/重算工作时，再讨论其 chunking。不得假定 P 分块会自动形成 chunk 级 KV 流水传输，须从 connector 的实际发送/接收日志确认。

最小实验采用一个代表性负载、两个 budget、L0/L1 四格；若已有 S1 结果可以复用，只补缺格。随后选择 O-BASE/O-WS 或 R-baseline/R-new 中最相关的一组，在第二个 budget 上补一对运行，避免扩成全矩阵。

### 6.3 V：量化作为计算与容量变化变量

**量化定位为策略泛化与资源敏感性实验，不预设本轮开发新量化算法。** 权重量化与 KV 量化改变的对象不同，必须分开设计。

| 配置 ID | 权重 | KV | 优先级与要求 |
|---|---|---|---|
| V-BASE | 主模型 BF16 | 模型默认 dtype | 主结果基线 |
| V-W4 | 同一模型来源的 4-bit AWQ 或 GPTQ，选择一种 | 与 V-BASE 一致 | P2 首选；检查 3080 Ti、模型 shape、激活 dtype 和实际 kernel |
| V-KV8 | 与 V-BASE 一致 | 受支持的 FP8 KV 格式 | 更后置；attention、scale、LMCache 与 PD 全路径验证后再用 |
| V-W4-KV8 | 4-bit 权重 | FP8 KV | 本轮通常不做；不能跳过前两种独立验收 |

3080 Ti 为 Ampere/SM86；当前文档列出 AWQ/GPTQ/Marlin 的 Ampere 支持，因此可从兼容的预量化 checkpoint 中选一种作候选。硬件表不保证当前模型/轮子/后端已经可用，启动日志必须确认实际使用的 kernel，不能只依赖模型名称或参数。

不把原生 FP8 W8A8 GEMM 加速作为这张卡的默认路径；FP8 KV 存储又是另一件事，不能仅因没有原生 FP8 Tensor Core 就断言所有 FP8 KV 路径不可用。它依赖具体 attention 实现和转换能力，应单独验收，不预设兼容。

#### 6.3.1 模型来源与执行门槛

- 优先选择与主模型同系列、同规模、可核对来源的现成预量化权重，记录 base revision、量化方法、group size、zero-point、激活 dtype、tokenizer/template 与文件哈希。
- 实际权重需要通过 HuggingFace 镜像获取；先确认剩余磁盘、下载速度和模型来源，不新增大模型仅为测试量化。
- 原 checkpoint 的校准材料未知时写“未知”，不声称完全控制了量化误差。自己校准则需要单独时间、样本和依赖授权，本轮默认不开展。
- 不因加载预量化权重而安装已弃用的 AutoAWQ 训练工具；推理依赖是否缺失先检查，任何安装仍遵守本机规则。
- 若 kernel 只能使用 FP16 激活，增加 FP16 非量化桥接基线，或明确将激活精度列为共同变化；不把全部差异归于权重 bit 数。
- 初始额外兼容/下载排查时间盒为 20～30 分钟；明显需要重编译、重建环境或长时间下载时延后，不消耗核心实验与复验窗口。

#### 6.3.2 权重量化：拆开计算变化与缓存扩容

权重变小可能让更多显存分配给 GPU KV，进而改变抢占、CPU offload 和缓存淘汰。这是有价值的系统效应，但不能混同于算法增量。

采用两类口径，时间不足时先做第一类：

1. **同 GPU KV token 容量：** 以两种精度都能支持的较小容量为准，固定最大上下文、并发、C、CPU 缓存与到达轨迹。重做 prefill/decode profiling，再在各自精度内部比较默认/改造策略。
2. **同 GPU 显存预算、自然 KV 容量：** 使用一致的内存预算规则，记录启动后实际权重、激活/graph、传输缓冲与 KV 容量；量化释放的显存允许转化为更多 KV，再观察 offload 和本地抢占收益是否减弱。

在两种精度内分别计算策略增量：`Gain_BF16 = 改造_BF16 对默认_BF16`、`Gain_W4 = 改造_W4 对默认_W4`。不能只拿“量化+新策略”与“BF16+默认”比较并声称都是调度收益。

#### 6.3.3 KV 量化：重新计算字节与正确性

- KV 的字节/token、CPU 工作集估计和写入/加载成本全部按实际存储布局重算。
- “同字节预算”与“同 token 容量”分开报告：前者可容纳更多 token，后者可以降低传输与存储字节，不能混作同一控制条件。
- 权重量化通常不直接减少每 token 的 KV 字节；KV dtype 未改变时，不能因为权重变成 INT4 就把工作集估计除以四。
- 验证后端保存/恢复的是量化 KV 还是转换后的表示，以及 scale 的保存、传输、恢复和生命周期；名义 FP8 不保证 CPU 存储或链路字节按比例降低。
- PD 两端采用一致且兼容的权重、KV dtype、scale 与布局，验证真正复用及非强制输出；不混接不同量化 checkpoint 生成的 KV。
- 以实际传输字节、恢复量与运行时延报告结果，不按理论 bit 数推算性能收益。

#### 6.3.4 数值与任务质量

- 同一精度内部，默认/改造仍应通过缓存与传输正确性检查。
- 跨精度不要求逐 token 完全相同；另做非强制 greedy、结构化输出或少量可执行代码样例检查，并在可用时补固定小评估集的 loss/任务分数。
- 小规模检查只能提供回归信号，不足以证明“精度无损”或 SWE-bench 成功率不变；报告样本数、具体检查与观察到的退化。
- 强制历史输出的性能回放不能用于证明量化后的生成质量。
- 如需校准，校准集与质量评估集分开，不能用正式评估数据挑量化设置。

### 6.4 C/V 的最小追加矩阵与顺序

| ID | 变量 | 最小比较 | 目的 |
|---|---|---|---|
| X-C1 | 两个 chunk budget | 各自 L0/L1，2×2 | 本地调度对粒度的敏感性 |
| X-C2 | 第二个 chunk budget | 固定其余参数，补 O-BASE/O-WS 或 R-baseline/R-new 一对 | 避免只在单一粒度有效 |
| X-C3 | chunking 开/关 | 合法且相同的大预算，固定其他参数 | 开关对照；无实际分块时如实标注 |
| X-V1 | BF16/W4 | 每种精度各做默认/改造，2×2 | 检查策略迁移，同 KV 容量口径优先 |
| X-V2 | KV dtype | 先单卡正确性，再同 dtype 内默认/改造 | 字节、工作集与成本变化；通过后才上 PD |

顺序：**主 R/O/L 结果 → X-C1 → X-C2 或 X-C3 → X-V1 → X-V2**。若预算只容纳一组扩展，优先 X-C1。BF16 主线无需因量化兼容问题暂停；不执行 `架构×R×O×L×C×V` 全排列。

## 7. 改造 R：借鉴 Preble 的请求放置

### 7.1 基线与逐项增量

| ID | 策略 | 用途 |
|---|---|---|
| R-RR | Round-robin | 简单参照，不作为唯一基线 |
| R-LOAD | 最低在途/排队请求数 | 负载基线 |
| R-TH | 前缀亲和 + 绝对/相对负载差距阈值 | 与已有 Router 同类规则的直接基线 |
| R-WORK | R-TH 中用工作量代替请求数 | 隔离负载估计贡献 |
| R-COST | 工作量 + 新请求成本 + 淘汰损失代理 | 主改造 |
| R-TIER | 在 R-COST 中区分 GPU/CPU 加载成本 | 外部状态可靠时追加 |

所有路由对照共用目录来源、刷新周期、分词方式和请求登记逻辑；需要改变目录实现时单独消融。重实现基线应注明对应官方版本和行为差异。

### 7.2 前缀目录

- 使用 token 级连续前缀；可用压缩前缀树或与引擎兼容的块哈希链。
- key 至少绑定模型/tokenizer/template、精确前缀、必要的 LoRA/cache salt 等身份。
- 对每个实例记录 GPU 确认驻留、CPU 确认驻留、待保存、待加载和未知状态。
- GPU 与 CPU 重叠前缀只计一次；CPU 只提供 GPU 已有部分之后的新增连续覆盖。
- 首选实际 KV events/状态快照。若先用请求历史推测，应标记 `inferred`，设置过期与失效，并用实际命中评估误差。
- 请求完成不自动证明 KV 仍驻留；已发起保存不等于 CPU 已经有可用副本。
- 处理驱逐、保存失败、事件缺失、实例重启和 generation/epoch 变化；未知状态降低收益估计。
- 同实例的 CPU KV 与跨实例共享 CPU KV 是不同配置，第一版不混用。

### 7.3 工作量与成本模型（工程适配，非论文原式）

```text
Cost(i, r) = Q_est(i)
           + Path_est(i, r)
           + EvictPenalty_est(i, r)

Path_est = GPU 命中后的剩余 prefill 成本
           或外部加载与剩余 prefill 的预计关键路径成本
```

- `Q_est` 由排队剩余 prefill、活跃 decode 与已发出但尚未被引擎观测的请求估计，单位统一为毫秒。
- 初版使用长度分桶、低并发 profiling 和滑动平均，不预设 token 与耗时严格线性。
- 引擎快照与 Router 账本对齐时，将已观测请求从 pending 转入 observed，避免重复计费。
- 对输出长度仅用可见预算/历史分桶；不把 `max_tokens` 当作真实剩余输出，也不用评估轨迹的未来值。
- 加载与计算有重叠时用实测有效路径模型；不能机械相加所有独立耗时。
- 计算成本与队列成本分别定义，避免重复累计同一批工作。
- 预测误差和各成本分量要写入决策日志；模型首先服务于排序，不宣称精确预测。

### 7.4 淘汰损失代理

目标是比较新请求可能挤出已有缓存的后续损失，而不是直接改写引擎淘汰语义。

```text
EvictPenalty_est(i, r)
≈ sum(可能受影响的唯一前缀片段重算成本 × 历史复用权重)
```

- 根据实际可用 GPU 空间、请求新增 KV 需求和候选缓存块估计压力。
- 被运行请求引用、被传输 pin 的块不能视作立即可回收。
- 共享祖先与重叠前缀去重，不能按会话重复计算同一物理 KV。
- 只对有限候选或聚合统计估计，避免每次路由扫描全部缓存。
- 只有聚合容量而没有可靠候选顺序时，使用粗粒度压力代理并明确标注；不写成精确预测真实 victim。
- 若状态采集成本过高，先完成 R-WORK，R-COST 降为待验证扩展，禁止虚构淘汰代价结果。

### 7.5 突发登记与稳定性

- 选中实例后立即登记 request ID、预计工作量与开始时间；失败/取消/结束时恰好释放一次。
- 快照陈旧、目录不完整或估计误差过大时，退回预先固定的负载规则并记录原因。
- 如观察到阈值附近振荡，再增加滞回；记录滞回带来的冷实例探索减少。
- 重定向后在新实例自然计算出的 KV 可形成副本，称为“通过请求放置预热”；没有真实数据迁移时不称 KV 迁移。
- 缓存目录仅影响性能选择，不作为实际跳过计算的正确性依据；最终是否可复用仍由引擎确认。

### 7.6 CacheRoute 备选路线

若实时 GPU 状态/淘汰成本接入明显超时，可改用：近期前缀访问率 → 稳定候选实例集合 → 按预期工作量放置 → 候选集合内低负载选择 → 定期重规划。

prefix key 必须对应实际稳定 token 片段；不能只用 repo ID 认定命中。大型长前缀与短前缀应按字节/计算成本区分，不能无条件照搬等大小 slot 模型。

该路线与 R-COST 选择其一作为主要交付，另一条只保留方案和边界，避免分散实现时间。

## 8. 改造 O：工作集压力感知 CPU KV 写入准入

### 8.1 实验策略

| ID | 行为 | 作用 |
|---|---|---|
| O-OFF | APC 保持相同，关闭 CPU KV | 证明外部缓存的基础效果 |
| O-BASE | 兼容版本 LMCache 默认保存/恢复 | 直接基线 |
| O-FIX | 固定过滤大规模新增写入 | 证明始终过滤的收益与损失 |
| O-WS | 只有工作集与容量反馈显示压力时，才过滤大规模写入 | 主改造 |
| O-LAZY | LMCache MP 的现成 lazy offload | 相应模式可用时的较强保存路径对照 |

如新增 copy-time 去重，先让 O-BASE/O-FIX/O-WS 共用相同去重，或另设仅去重对照。不得把去重与准入同时启用后，将全部收益归给准入。

### 8.2 工作集估计与压力

先实现低成本在线近似，并留出离线栈距离分析接口：

```text
W_est(i) ≈ (A_recent(i) - 1) × N_recent(i) × KV_bytes_per_token
pressure(i) = W_est(i) > CPU_capacity(i)
              AND CPU tier 接近满载
              AND 近期确实发生容量淘汰
```

- `A_recent` 是近期活跃会话/任务数，包含工具等待期间仍可能返回的会话，不是当前 HTTP 在途请求数。
- `N_recent` 是历史观测的上下文长度统计；估计值仅反映近似尺度。
- 该近似适用于类似长度、交错访问的积压会话；长短差异、共享前缀和不规则工具间隔会造成误差。
- 有条件时使用前缀去重字节或离线栈距离曲线检验估计，不能声称近似具有精确驻留保证。
- KV 字节/token 从当前模型、KV dtype、TP 与实际布局计算，和实际 CPU 分配量校验，不能沿用作者模型的常量。
- 第一版按实例估计；Router 改变会话归属后重新观察局部工作集，避免将所有任务重复计入每个实例。

**容量观测的口径必须核对。** 当前 native `CPU_CACHE_USAGE_PERC` 等指标描述传输 pin 占比，并不自动等于已驻留缓存占用。工作集策略需要真正的 resident/registered chunks、总容量及容量淘汰数，不能误用同名指标。

### 8.3 写入决定

在第一次已解析的前缀查询后，计算请求需要新增保存的完整 chunk 数 `u`：

```text
if pressure and u > write_threshold_chunks:
    本请求跳过可选 CPU KV 保存
else:
    沿用后端正常保存路径
```

- `u` 来自后端确认已保存的连续前缀和本次提示长度，不直接把 GPU 命中长度当成 CPU 已保存长度。
- 小规模追加倾向保留，缺失历史的大规模回填在压力下受限。
- 每个逻辑请求首次决定后冻结；chunked prefill、重复 lookup 和抢占恢复不能反复翻转。
- 没有压力时退化到正常保存，允许新会话和大上下文进入 CPU。
- 门限按 chunk 大小和 trace 长度标定；作者门限不是本机默认最优值。
- O-WS 应记录“估计超容量、满载、正在淘汰”各自是否成立，不能只有最终布尔值。

### 8.4 接入与生命周期

- 优先使用自定义 connector/module path，保留 LMCache lookup、restore、序列化和底层传输逻辑。
- 当前分支 bundled adapter 已见请求级 `lmcache.skip_save` 读取点；实际运行使用 native/bundled 还是外部 adapter 必须记录并验证。
- scheduler 与 worker 的参数传播必须验收，避免 scheduler 打印 skip 而 worker 仍保存。
- request ID、逻辑 generation、抢占恢复、完成和取消之间的状态释放要一致；不能长期泄漏任务表与决定表。
- 元数据仅做只读采集，不在 Top-W 遍历中重复调用会改变 connector 状态的 lookup。
- 采用外部 connector 源码时保留其许可与作者来源；复制接口后需重新做版本适配和行为验证。
- 遥测过期时本项目默认采取“恢复正常保存并记录降级”的保守路径；这与作者某些缺省估计回退方式不同，属于明确的适配选择，需要单测与报告。

### 8.5 PD 的特殊边界

**可选 CPU 备份与 P→D 必需 KV 交接必须分离。**

- 不得因为 CPU 写入压力而跳过 D 启动所必需的数据传输。
- bundled adapter 已对 disaggregated transfer 的 skip-save 做特殊处理，迁移时保留语义。
- 第一阶段在单卡/双完整副本实现 O-WS，PD 初期关闭该修改或仅作用于已验证的独立 CPU 缓存通道。
- 未验证组合 connector 对同一 token 的所有权、分配和完成通知之前，不同时叠加 PD connector 与 CPU offload。

### 8.6 验证机制与负结果

- CPU 层不足：观察写入后未读即淘汰、写/读比例、重算和会话尾延迟。
- CPU 层临界：观察过滤是否帮助部分前缀存活，是否损害新会话。
- CPU 层充足：O-WS 应尽量恢复 O-BASE 行为；O-FIX 可能回退。
- 若 O-WS 只减少写入却增加重算，要按最终时延/goodput判断，不能只汇报带宽节省。
- GPU 工作集本就能装下、CPU 从未实际加载时，该配置只能证明额外开销，不能证明 offload 优化有效。
- 加载/重算成本决策留作 P2：先测到有意义交叉区间再做，且区别于最新 LMCache 已有策略接口。

## 9. 改造 L：已有实例内调度的保留与适配

### 9.1 策略分级

| ID | 内容 | 本次地位 |
|---|---|---|
| L0 | 当前分支默认准入与抢占 | 基线 |
| L1 | 已有 cache-affinity 准入、aging、恢复成本感知抢占 | 必须重新评估 |
| L2 | 在 L1 中接入外部 KV 就绪/成本信息 | 观测证明有必要后追加 |

L1 的具体参数要单独列出：`admission_policy`、`preemption_policy`、Top-W、aging、prefix eviction policy。不能把所有非默认开关都混成一个不可拆解的“优化版”。

本轮主比较可以固定一组 L1；在代表性场景追加“只改准入、只改抢占、两者均改”，不要求全部架构重复完整拆分。

### 9.2 已有语义必须保留

- 用户优先级是硬约束，不跨优先级任意重排。
- Top-W 为 waiting 候选范围，不自动等于 running chunk 每轮重新排序。
- aging 提供排序保护，不保证资源不足时立即执行，也不代表跨实例公平。
- waiting 分配失败不等于立即抢占 running；按当前调度路径判断。
- prefill chunk 与 decode 的续算都可能触发 KV 压力。
- 物理块共享、deferred free、传输 pin 都会影响立即可回收量。

### 9.3 L2 的最小可行范围

若实际 trace 显示 CPU/远端加载改变了排序价值，可扩展只读候选特征：

- GPU 已就绪连续前缀。
- CPU 已确认且可加载的连续前缀。
- 外部 lookup 未完成、保存未完成、加载中、加载失败状态。
- 预计剩余计算与加载路径，不将全部外部命中当成零成本。

只对 ready 请求做候选比较；等待传输完成的请求继续走既有 blocked/ready 流程。不能把未加载 KV 伪装为 `num_computed_tokens`，也不能为排名强行分配或 pin 块。

抢占适配需从实际恢复方式出发：本地重算、CPU 恢复、P→D 重传或重新 prefill 的成本并不相同。若无法可靠观测，先保留 L1 并报告 D 端信号失效，不临时发明未经验证的恢复路径。

本地 KV generation 只管理本地派生特征失效，外部副本状态需要独立 epoch、时间戳与完成通知。

## 10. 单卡实验：建立机制与新硬件基线

### 10.1 S0：环境与正确性

执行顺序：

1. 记录 Git、Python/import 路径、GPU、驱动/runtime、cgroup、存储和依赖信息。
2. 确认模型文件完整，启动单卡普通推理。
3. 先用短请求验证服务，再用共享前缀、多轮和长短混合请求验证。
4. 记录自然 KV 容量与内存余量，再决定压力档。
5. 路径可用后接入 LMCache，验证首次写入与二次读取。

验收要求：无异常/挂起；模型/请求身份正确；输出检查通过；运行日志能确认实际代码和参数；缺失依赖明确列出，不能一边静默安装一边修改环境。

### 10.2 S1：本地策略与 chunking

| 实验 | Offload | 本地策略 | 其他参数 |
|---|---|---|---|
| S1-A | O-OFF | L0 | 固定主参数 |
| S1-B | O-OFF | L1 | 与 A 相同 |
| S1-C，P1 | O-OFF | L0/L1 | 按 X-C1 补第二个 budget 的两格，构成 C×L 对照 |

验证 L1 在 3080 Ti+3B 上是否触发，得到新硬件基线。旧实验的约 4.20% 吞吐收益仅作历史背景。

同一 budget 内比较 L0/L1，再比较两个 budget 下的策略增量；实际 chunk 大小、跨轮次数、每轮调度开销与 ITL 一并记录。不能仅调整 budget 后把绝对吞吐变化计为 L 的收益。

### 10.3 S2：offload 机制验收

固定 L0，以 W4 构造：

1. A 前缀完成计算并成功保存到 CPU。
2. 访问其他前缀，确认 A 的 GPU 缓存覆盖下降。
3. A 再次出现，确认 GPU miss 部分实际从 CPU 恢复。
4. 对比 O-OFF 下同请求的实际重算量。

必须区分 cache lookup、GPU hit、CPU hit、开始加载、成功完成加载。仅打印“LMCache initialized”或“存在命中”不算验收通过。

### 10.4 S3：O-WS 的核心消融

先对 O-BASE/O-FIX/O-WS 在一个压力容量上筛选，再对最关键对照覆盖不足/临界/充足三档。

L 固定 L0，GPU KV 容量固定；CPU 后端、块大小、dedup、异步配置相同。CPU 容量变化属于本节明确干预，不与其他变量同时改。

核心结论应能回答：过滤在哪个压力区间有效，容量足够时是否及时关闭，净收益来自减少写入、增加有效恢复还是减少抢占。

### 10.5 S4：offload 与本地策略的相互作用

在一个已验证的 CPU 压力档运行：

| 组别 | CPU 策略 | 本地调度 |
|---|---|---|
| S4-A | O-BASE | L0 |
| S4-B | O-BASE | L1 |
| S4-C | O-WS | L0 |
| S4-D | O-WS | L1 |

该 2×2 设计可区分两个模块的增量与相互作用。如果时间紧，只补已有其他运行中缺失的格子，避免重复执行。

## 11. 双完整副本：路由主实验与三层闭环

### 11.1 D0：部署与路由正确性

- 两个 TP=1 实例，模型和配置一致，独立端口、engine ID、日志与 CPU 缓存空间。
- 同一 client 通过 Router 发送，保存 request→instance 映射。
- 检查流式转发、错误、取消、客户端断开和请求完成后的账本清理。
- 通过实际 token 前缀与引擎命中交叉校验目录，统计误报/漏报。
- 两卡尽量固定为同一对；更换卡对时重新校准并记录。

### 11.2 D1：R 的独立消融

固定 O-OFF、L0，按 R-LOAD → R-TH → R-WORK → R-COST 筛选，R-RR 只需一个代表性参照。

使用 W2 并补 W3 或 W0。观察前缀复用、实际剩余 prefill、队列失衡、路由开销和尾延迟。

加入 R-TIER 时固定 O-BASE、L0，比较 R-COST/R-TIER；不能用 O-OFF 的 R-COST 与 O-BASE 的 R-TIER 直接归因层级信息。

### 11.3 D2：R/O 的核心组合

固定 L0，选择已经跑通且最有代表性的 `R-new`（R-COST 或 R-TIER）：

| ID | 路由 | CPU 保存 |
|---|---|---|
| D2-A | R-TH | O-BASE |
| D2-B | R-new | O-BASE |
| D2-C | R-TH | O-WS |
| D2-D | R-new | O-WS |

以上既能证明各自增量，也能观察路由改变会话分布后，CPU 工作集是否发生变化。四格使用相同后端与目录语义，不能混用不同 LMCache 模式。

### 11.4 D3：本地策略最终增量

- D3-A：R-new + O-WS + L0，可复用 D2-D 的合格结果。
- D3-B：R-new + O-WS + L1。
- 如 L2 已通过正确性检查，追加 D3-C；否则不阻塞交付。

这是面试主线最关键的组合：在已有系统能力和新增路由/保存策略之上，本地调度还解决什么问题。

### 11.5 反馈与稳定性

R 改变会话分配 → 每实例工作集变化 → O 改变保留内容 → R 下一轮观察到的缓存变化。

先固定模型参数完成单层消融，再观察联合运行，记录短时间内改路由、压力开关和缓存命中是否振荡。不在正式评估中持续人工调参。

### 11.6 C/V 的选择性迁移

单卡 X-C1 通过后，在一个代表性双副本场景补 X-C2，确认成本重标定与 CPU 写入决定在分块变化后仍合理。

量化优先先做单卡 X-V1；若两实例均能用同一量化配置正确启动、剩余时间允许，再补最强基线/组合策略一对。量化不会免除 Router 的缓存目录失效和模型身份隔离，旧 BF16 目录与 CPU KV 不跨 checkpoint 复用。

## 12. 1P1D：早期验收与角色消融

### 12.1 E-PD：前两小时内尽早尝试的最小验收

这一阶段只验证技术路径，不等待 R/O 全部完成。

1. 确认所选 connector 与依赖版本，优先现有官方示例和最小模型。
2. 用 GPU 2/3 启动 P、D，分配唯一 API/side-channel 端口。
3. 启动最小代理，记录 P 计算与 D 收取 KV 的请求关联。
4. 在验收配置中禁止或显式监测失败重算回退；可用时选择 `kv_load_failure_policy=fail`，避免假传输成功。
5. 确认传输完成量、D 使用的远端覆盖及未重复完整 prefill。
6. 对照聚合引擎进行小批 greedy/固定 token 正确性检查。
7. 记录 backend、路径与有效传输时间；拓扑可见不等于 P2P 可用。

**通过条件：确有 KV 数据传输、D 确实利用、请求正确完成。** 两个独立服务串联或请求回退到 D 完整重算，均不算通过。

若小模型通过而 3B 不通过，记录模型/内存差异，不能使用小模型性能替代主实验。

### 12.2 P1：P/D 两端本地策略消融

固定 connector、代理、模型、P/D 资源与 O 配置：

| ID | P 本地策略 | D 本地策略 |
|---|---|---|
| P1-A | L0 | L0 |
| P1-B | L1 | L0 |
| P1-C | L0 | L1 |
| P1-D | L1 | L1 |

优先确认策略实际触发和决策变化，再比较端到端延迟。D 原有 prefill 特征无区分度时保留负结果，不仅选择 P 端的有利数据。

如资源压力和剩余时间不允许完整四格，先 A/B/D 筛选，并明确缺少 D 独立效应，不能作完整因果分解。

### 12.3 多轮与双向复用

当前分支有多轮代理示例，可跟踪 D 返回的 `kv_transfer_params`。但以下事项需逐项验证：

- session 对应正确的 D 与有效块，TTL、重启、失败后能失效。
- 下一轮 P 真正获取并利用之前的历史，而非仅返回同一个 D。
- 输入历史的实际 token 前缀一致，远端覆盖连续且块边界正确。
- 单向 P→D 和双向历史复用分开标记，不能只因存在代码示例就宣称已启用。

首轮使用单向路径建立正确性和性能基线；双向复用为 P1 扩展，不与其他修改同时首次启用。

Chunked Prefill 扩展先只改变 P 端 budget，验证实际传输行为；D 端不因是独立角色就假定没有任何 prefill/恢复工作。量化迁移先要求 P、D 使用一致配置且通过所有数据与 scale 的正确性检查，再做性能，避免同时首次引入量化、双向复用和新路由。

### 12.4 排错时间盒与备用路径

- connector/传输兼容排查累计初始预算 60～90 分钟。
- 优先定位 imports/ABI、GPU 映射、端口、缓冲容量、backend/UCX 与传输回退，不直接重装整个环境。
- NIXL 使用其 backend/UCX 配置，不能以 NCCL 参数作为通用修复。
- 如选择可验证的 CPU 中转或文件型路径，应明确标记“功能参照”，不能外推为高速互联 PD 性能。
- 未完成依赖安装授权、存在大范围 ABI 冲突或需要宿主机改造时，记录阻塞并推进单卡/双副本；不让 PD 阻塞全部交付。

## 13. 2P1D / 1P2D / 2P2D：按证据扩展

### 13.1 三卡阶段是否需要

三卡不是强制前置；按 1P1D 的瓶颈选择：

- P 队列长、D 有余量：尝试 2P1D，先验证 P 端放置。
- D decode/容量受限、P 有余量：尝试 1P2D，先验证 D 端负载选择。
- 已确定四卡链路且时间充足：可直接 2P2D，但保留 1P1D 基准。

### 13.2 Q0：2P2D 正确性与资源映射

- 四个独立 TP=1 引擎，分别具备唯一 engine ID、API/side-channel 端口和日志目录。
- 固定 P0/P1/D0/D1 到物理 GPU 的映射，记录各 P→D 路径。
- 验证四种 P-D 配对均能完成真实传输，尤其跨 NUMA 路径。
- 目录按 role+engine+epoch 隔离；一次重启后不能继续使用旧块引用。
- 每请求记录选中 P、D、P 排队、P 计算、传输等待、D 排队及 decode 时间。
- 先禁止自动重试或记录每一次重试，避免失败被隐藏在最终成功率中。

### 13.3 P 与 D 的规则不同

P 端优先使用缓存/工作量/淘汰损失评分；D 端优先考虑活跃 decode、GPU KV 余量、传输和排队。

不能直接把 P 的“剩余 prefill”成本公式复制给 D。D 同角色选路的缓存收益必须建立在已实现的实际历史复用流程上。

### 13.4 Q1：两端路由消融

固定 L0 和 CPU 配置：

| ID | P 端选路 | D 端选路 |
|---|---|---|
| Q1-A | 固定现成基线 | 固定现成基线 |
| Q1-B | P 改造 | 基线 |
| Q1-C | 基线 | D 角色适配策略 |
| Q1-D | P 改造 | D 角色适配策略 |

若 D 没有新策略，仅使用现成低负载/会话规则，应如实命名；不为了填满矩阵虚构“D 端创新”。

### 13.5 Q2：三层能力迁移

只有独立 CPU 保存路径与 PD 必需传输已解耦并通过验收，才开展：

- 最强 PD 路由 + O-BASE + L0。
- 相同路由 + O-WS + L0。
- 相同路由 + O-WS + L1。

时间不足时，交付 Q1 与 P1，O-WS 仍以双完整副本证据为准。组合未跑通不写成已完成。

### 13.6 Q3：同资源架构对照

- 1P1D 对双完整副本；2P2D 对四完整副本。
- 若报告三卡架构性能，相应参照为三完整副本。
- 固定 GPU 数、型号、模型、总请求工作和调参预算；记录实际显存与 CPU 内存开销。
- CPU 缓存若只部署在 P，架构对照应控制总 CPU KV 预算，或明确额外给出每角色预算与不可比之处。
- chunk budget 等角色参数可以在相同调参预算下分别选取；不能把某架构的明显坏配置作为唯一基线。
- GPU 总数相同不等于所有资源细节相同，结合模型副本开销、传输缓冲与拓扑解释。
- 报告 TTFT 与 ITL 的权衡及 SLO goodput，不承诺 PD 必然提升原始吞吐。
- C/V 扩展仅在基础架构对照之后，选择一个代表性配置验证；两种架构使用相同精度，并分别报告其合法 chunk 参数，不额外铺开全矩阵。

## 15. 正确性检查与必要测试

这些改造影响状态和调度，应做针对实际风险的测试，而非大量复刻实现的断言。

### 15.1 R 的行为检查

- 长短请求数相同时，工作量规则能区分实际压力。
- GPU/CPU 重叠命中不重复计算；不同版本/epoch 不共享错误目录。
- 突发请求登记后，后续请求能看到新负载；快照对齐不重复计算。
- 完成/取消/错误释放账本恰好一次；失联实例不能被正常选中。
- 构造已知冷热前缀，比较预测命中与引擎实际命中，量化目录误差。

### 15.2 O 的行为检查

- 无压力时 O-WS 与正常保存语义一致；真实压力且大回填时会拒绝保存。
- 小追加仍允许；重复 lookup/chunk/抢占后决定不翻转。
- 真驻留容量与传输 pin 口径分开；过期遥测按约定降级。
- request ID 重用、完成、取消和异常路径不串状态。
- 跳过保存不改变本次计算输出，CPU 恢复失败后回退/失败路径按配置可观测。
- PD 必需传输不受可选保存过滤影响。

### 15.3 L 与 PD 的检查

- 保持用户优先级、aging、候选范围和 blocked/ready 语义。
- 不把外部未就绪 KV 当作已计算；共享块与 deferred free 的回收量不虚报。
- P、D 使用一致的模型与 token 身份；所有配对完成实际传输。
- 对比无缓存、GPU 缓存、CPU 恢复、PD 路径的非强制输出。
- 批处理/浮点非确定性导致少量 greedy 分歧时，先与相同路径的重复运行比较，再定位缓存错误；不能用“文本看起来合理”代替校验。

### 15.4 C/V 的追加验收

- 关闭 chunking 的预算配置合法；开关实验预算匹配，实际是否切分可证明。
- 多个 prefill chunk 不重复记录会话、不翻转首次 CPU 保存决定；末尾不完整存储 chunk 按后端约定处理。
- 量化使用的实际 kernel、dtype、模型来源和 KV 容量已记录；各成本模型按配置重标定。
- KV dtype/scale 在 GPU、CPU 恢复及 P/D 之间一致；跨 checkpoint 不错误命中。
- 强制输出回放与非强制质量评估分开；未通过质量检查的配置不作为无损提速成果。

先运行受影响的现有测试和新增的必要行为测试，再做小规模真实服务验收。通过后不为凑数量反复运行无关全量测试。

## 16. 测量、统计与公平比较

### 16.1 主要指标

| 类别 | 指标 | 口径 |
|---|---|---|
| 服务目标 | request goodput | 成功且满足预先指定 TTFT/TPOT 或 E2E 条件的请求数 / 统一测量时长 |
| 有效输出 | SLO-qualified output tok/s | 上述合格请求的实际输出 tokens / 同一时长 |
| 延迟 | TTFT、TPOT、E2E、会话完成时间 | client 单调时钟；分首轮/后续轮和长短请求 |
| 流式体验 | ITL / chunk 间隔 | 说明是否能观察 token 级；不能将 chunk 间隔冒充逐 token ITL |
| 计算 | 实际 prefill、恢复重算、抢占次数 | 明确是否含 warmup、是否能区分 resume |
| 缓存 | GPU/CPU 确认命中、实际恢复、存活到再用的比例 | 避免只看目录或 lookup 命中 |
| 传输 | 保存/恢复字节、排队、完成时间、有效带宽 | 按物理方向和实例汇总 |
| 路由 | 选路原因、预测误差、目录误报/漏报 | 各成本分量和降级次数 |
| 资源 | GPU 内存/利用率、CPU/RSS、pinned/shm、I/O | 按实例及总量 |
| 公平性 | 冷/热会话等待、最大等待、各类请求尾延迟 | 不仅报告整体平均 |
| 正确与可靠性 | 错误、超时、重试、取消、输出检查 | 不静默丢弃失败请求 |

TPOT 通常按 `(E2E - TTFT)/(output_tokens - 1)` 计算；不足两个 token 的请求单独处理。多个 token 合并在首个流式 chunk 时，需说明该近似与精确 token 时间的区别。

### 16.2 SLO 与测量边界

- 在调参集上选定延迟目标，正式评估前冻结；可给少量预先定义的目标点，不看结果后挑最有利门限。
- 固定请求集合和 arrival/依赖规则，warmup 是否计入与缓存状态必须一致。
- 开环容量实验固定发出窗口，统计该窗口内到达请求，等待 drain 并保留超时；明确 goodput 分母，不遗漏窗口末尾慢请求。
- 闭环 Agent 实验报告全任务 makespan、会话完成时间及工具等待口径，不将其直接当作开环最大容量。
- 同步记录 client、Router 与引擎时间；跨进程阶段使用关联事件，不能简单相加不同总体的 P95/P99。

### 16.3 重复与不确定性

- 单轮筛选只用于决定下一步，不作稳定提升结论。
- 决赛选择两三个核心对照，至少三轮独立、交错/配对运行；保留每轮值和方差。
- 硬件争用或后台负载异常时标记运行，不只删除不利样本；剔除标准预先固定。
- 尽可能积累数千请求再讨论尾部，实际样本不足时 P99 只作描述，主结论使用更稳定指标及分组结果。
- 同会话请求相关，重采样优先以 session/run 为单位，不假设所有请求独立。
- 收益必须高于波动并能解释；结果“在噪声内”应如实写出。

### 16.4 固定资源与配置

- 路由比较固定 GPU 数、卡对、后端、CPU 容量、L 策略和目录实现。
- offload 比较固定 GPU KV、CPU 容量、替换与 dedup；容量扫描仅改变容量。
- L 比较固定 R/O；PD 两端消融固定角色资源和传输路径。
- 不将 4090+7B、3080 Ti+3B、1/2/4 GPU 的原始吞吐直接混为策略提升。
- 不能以单个更高命中率、较少写入或更高利用率代替最终服务收益。
- C 实验区分分块开关与每轮总 budget；V 实验区分同 KV token 容量、同显存预算与同存储字节预算。
- 权重/KV 精度改变后重算成本、缓存身份与工作集，不沿用原模型常量；先报告每种精度内部的策略增量。

## 17. 时间计划、实验取舍与停止条件

### 17.1 默认按 12 小时安排

这是排程模板，不是完成保证。实际获得面试时刻后，先锁定最后两小时的整理窗口，再反向调整。

| 1～2h | LMCache 基础及最小 1P1D 验收 | 可用路径与明确阻塞；T8 尽早尝试 |
| 2～4h | O-BASE/O-FIX/O-WS 与机制观测 | 单卡 offload 增量与容量边界 |
| 4～6.5h | 双副本 R 基线与工作量/成本改造 | 路由独立对照 |

### 17.2 时间不足时如何裁剪

| 剩余窗口 | 保留 | 延后 |
|---|---|---|
| 约 8～10h | O-WS、R-WORK/R-COST 的可行子集、双副本组合、最小 PD；能复用时补 X-C1 | 全部容量档、完整 2P2D 消融、KV 量化与复杂 V 组合 |
| 约 5～7h | 一个清晰新策略的实现与三轮对照，另一层机制验收 | 多套新路由、L2、复杂组合 connector、量化；C 只补最关键缺格 |
| 不足 4h | 复核已有可用成果、补关键缺口、整理证据 | 高风险传输重构和新后端 |

### 17.3 具体切换条件

- 单卡模型仍无法运行：优先解决普通推理，不同时调 Router 和 connector。
- 数据获取超 20～30 分钟无进展：先做标注清楚的机制负载，不停止其他独立工作。
- PD 排错累计超过初始 60～90 分钟：记录依赖/链路问题，回到双副本交付，后续有新证据再恢复。
- R-COST 所需状态不可低成本获取：交付 R-WORK，并考虑 CacheRoute 备选；不谎称已实现精确淘汰预测。
- O 从未发生有效加载：调整工作集/容量来验证机制，禁止直接总结 offload 收益。
- O-WS 从不触发或始终触发：核对压力口径与负载，补充相反容量区间。
- chunking 关闭配置不合法或峰值内存不足：记录限制，保留两个合法开启 budget 的交互实验，不同时更改上下文/并发混淆结论。
- 量化依赖、权重或 kernel 路径明显超出时间盒：保留 BF16 主线；不重建环境、不临时自研量化器。
- 量化释放显存后策略不再触发：报告瓶颈迁移，并用同 KV 容量对照解释，不能隐瞒无收益结果。
- 正确性检查失败：相关性能运行停止，保留日志并修复；不能靠忽略错误继续统计。
- 临近整理窗口：冻结参数与新功能，完成必要复验和说明；未稳定扩展标记实验性。

### 18.3 三条证据链

1. **R：** 评分/阈值 → 选中实例变化 → 实际排队与命中变化 → 延迟/goodput。
2. **O：** 压力观测 → 保存决定 → 驻留/淘汰/实际恢复变化 → 重算与会话完成时间。
3. **L：** 策略触发 → 准入/victim 变化 → 恢复与计算变化 → 最终服务收益。

只记录最终均值而没有中间机制，不能充分支持归因。
