```
RuntimeError: Task error: File reconstruction error: CAS Client Error:
```

**原因**：HuggingFace 新版默认用 **Xet 协议**下载大文件，但 Xet 的 CDN（`cas-server.xethub.hf.co`）不走 hf-mirror 镜像且需要认证，国内直连必挂。小文件（配置）走普通 HTTP 从镜像下载成功了，大文件（权重）走 Xet 就 401 失败。

**解决办法：禁用 Xet，强制走普通 HTTP（hf-mirror 就能代理）**。在你的终端逐条执行：

**第 1 条——环境变量禁用 Xet 并重新启动：**

```bash
export HF_HUB_DISABLE_XET=1
python -m vllm.entrypoints.openai.api_server --model Qwen/Qwen2.5-7B-Instruct --gpu-memory-utilization 0.9 --max-model-len 4096
```

**预期**：这次能看到 `model-00001-of-00004.safetensors` 等大文件的下载进度条（共约 15GB，走 hf-mirror）。

## 指标解释

| 指标 | 全称 | 含义 | 体验意义 |
|------|------|------|---------|
| **TTFT** | Time To First Token | 从发请求到收到第一个字的延迟 | 用户点“发送”后等多久才看到字蹦出来，**体感最关键** |
| **TTFT P99** | 99 分位首字延迟 | 最慢的 1% 请求的首字时间 | 衡量长尾体验（卡顿感） |
| **ITL** | Inter-Token Latency | 生成过程中相邻两个 token 的间隔 | 流式输出的“打字速度”是否流畅 |
| **输出吞吐** | Output Throughput | 全引擎每秒产出的 token 总量（所有请求加总） | 硬件利用率/服务容量，4090 跑 7B 的典型值就在 900-1000 |
| **请求吞吐** | Request Throughput | 每秒完成的请求数 | 服务能扛多少用户 |

## 结果解读

1. **吞吐线性扩展**：并发 1→16，吞吐 62.8 → 947.8 tok/s，接近完美线性——说明 vLLM 的 continuous batching 在满负荷利用 GPU，这是它对比朴素逐条推理的核心优势

2. **一个有意思的现象**：并发 16 时 TTFT 反而降到 0.07s——因为所有请求用同一个 prompt，**prefix cache 命中**了（之前请求已算过的 KV 直接复用）。这恰好就是你分支名 `kv-aware-scheduling` 要研究的东西：KV 复用对延迟的影响在这里体现得非常直观

3. **并发 1 时 TTFT 6.1s 偏高**：首请求包含 CUDA graph 预热 + 无缓存冷启动，属于正常现象；真实场景会在服务启动后先打几个预热请求

4. **ITL 稳定在 ~16ms**（约 60 tok/s 单流速度），P99 与均值差距小——流式体验流畅，没有调度抖动

## 过程中的关键发现（面试可讲）

1. **第一版没有 anti-thrashing 时 ITL p99 恶化到 3610ms**——被抢请求 `num_computed_tokens` 清零后重进 running 又是最小值，同一请求被反复抢（“钉子户受害者”），用户看到流式卡死。加一行 `num_preemptions` 作为第一序就修复到 1524ms
2. **抢占 -29% 且吞吐无损**：抢“进度最少”的请求，重算总量下降，腾出的算力被有效利用
3. ITL p99 仍比 default 高 13%——这正是 **P2（re-admission preference，被抢请求优先恢复）** 要解决的，设计文档 7 章已有方案

剩余 ITL p99 差距 + TTFT 长尾 = P2 的改进空间。继续 P2 吗？
